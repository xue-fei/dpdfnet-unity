## DPDFNet Microphone Demo 用 Loom 优化 IEnumerator（CaptureLoop 协程）

- 工程已自带 `Loom.cs`（`Assets/Scripts/DPDFNet/Loom.cs`）：`Loom.RunAsync(Action, onError)` 后台线程执行，`Loom.QueueOnMainThread(Action)` 回主线程；异常通过 `onError`/LogError 送回主线程（非吞掉）。`Initialize()` 建 DontDestroyOnLoad 的 GameObject 用 Update 泵送主线程队列。
- 改造 `DpdfNetMicrophoneDemo.cs`：原 `CaptureLoop` 每帧同步调用 `ProcessHop`（内嵌 ONNX 推理 8-16ms）阻塞主线程。改为把推理移出主线程：
  - `CaptureLoop` 切帧后调 `DispatchHop`（主线程：算 inRMS、背压判断、拷贝 hop、提交 `Loom.RunAsync`）。
  - `DoInfer`（后台线程：`processor.ProcessFrame` + 立即 `Array.Copy` 拷走结果；用 `inferLock` 把「推理+拷贝」包成原子）→ `Loom.QueueOnMainThread(() => CommitOutput(...))`。
  - `CommitOutput`（主线程：混合 playbackMix + 块级 AGC + 入 playbackQueue + 诊断）。
  - 关键：DPDFNet 是 stateful 流式模型，state 须逐帧串行传递，且 `ProcessFrame` 复用 `outHop` 返回。故 `inferLock` 串行化后台推理，保证帧顺序与缓冲不被并发污染。
  - 背压：`Interlocked` 计 `inflight`，超 `MaxInflight=2` 丢弃本帧（`droppedFrames` 计数已加入诊断日志 `drop=`），避免 ThreadPool 堆积与无限延迟。
  - `monitorBypass` 仍走主线程同步 `CommitOutput`（跳过模型）。加 `using System.Threading;`。
- 收益：主线程协程仅采集+提交，不被推理拖慢帧率；音频线程 PCMReaderCallback 独立供给播放不受影响。串行推理下处理速率仍受单帧推理耗时约束（实时边界 ~10ms/帧@16k），超预算则背压丢帧降质而非卡死。

## 修复 DpdfNetFileExample 输出比输入短 20ms（=n_fft）

- 现象：9.769s 的 mix.wav 处理完变 9.749s（差 0.020s = 320 样本 = n_fft）。
- 根因（对照本地 `DPDFNet/real_time_demo.py` 的 `STFTStreamingPreprocess`/`ISTFTStreamingPostprocess`，`DpdfNetAudio.cs` 1:1 复刻）：流式 STFT/ISTFT 是**因果**结构，每帧输出 `out_k` = 上一帧输入 `x_{k-1}`，即整体带一个 `hop`(160) 固定延迟，`out_0` 全 0。原示例有两处错：
  1. 只处理 `M=ceil(L/hop)` 帧 → 最后一帧真实输入的输出（`out_M`）永远没被冲出延迟线；
  2. 前导裁掉 `n_fft`(320) 且 `cleanLen = L-320` → 输出 `L-320` 样本（正好是 9.749s）。
- 修复（`DpdfNetFileExample.cs`）：处理 `M+1` 帧（末帧 0 补齐 flush），`outBuf` 长度 `(M+1)*hop`；裁前导 `hop`，取 `outBuf[hop : hop+L]`，得到与输入**完全等长**的结果（仅整体延迟一个 hop≈10ms@16k，属因果流式固有，非长度丢失）。并同步修正 README「离线处理文件」注与示例「关键逻辑」step3/4。
- 数值验证（纯 Python 复刻同一 STFT/ISTFT+本帧方案，identity 模型）：`len==L` 恒为 True，重建误差 ~1e-13（浮点精度），含 L=156304。说明长度 bug 已修、COLA 重建正确（与 real_time_demo.py 一致）。
- 注：DPDFNet 官方 `stream.py` 的 `StreamEnhancer`/`flush()` 用 win_len 缓冲 + 不同 OLA，与本 C# 移植的 real_time_demo 流式路径算法等价但非逐位一致（其 docstring 亦说明）。本工程文件示例基于 real_time_demo 路径。

## 修复 C# 处理结果与源码 DPDFNet 不一致（文件离线路径改用 center=True 算法）

- 现象：Unity C# 处理的音频与「源码 DPDFNet」处理结果不完全一致。
- 根因：文件处理参考 `DPDFNet/onnx_model/infer_dpdfnet_onnx.py` 的 `enhance_file_onnx`，它用的是 **librosa 的 `center=True` 反射填充 STFT/ISTFT** + `postprocess_spec`；而 C# 文件示例此前用的是 `real_time_demo.py` 的**因果流式 STFT/ISTFT**。两者帧对齐/边界处理不同 → 结果不同。`stream.py`/`real_time_demo` docstring 明确说与 `enhance`（center=True）非逐位一致。
- 修复 `DpdfNetFileExample.cs`：重写为严格对齐 `enhance_file_onnx` 的离线算法：
  1) 末端补 `win_len` 0（np.pad(waveform,(0,win_len))）；
  2) `center=True` 反射填充 `n_fft/2`（np.pad reflect，含 x[pad..1]/x[L-2..L-1-pad] 边界）；
  3) 逐帧 `rfft(win*frame)` → 流式 ONNX(state 回传，BuildInitialState 起始) → 逐帧 `irfft*win`，win² 归一化 OLA，两端裁 `n_fft/2`（librosa istft center=True）；
  4) `postprocess_spec`：裁前 `win_len*2`、补末 `win_len*2` 0；`fit_length` 到 L。
  - 自加 `ReflectPad`/`Rfft`/`Irfft`（Math.NET Forward 不缩放 / Inverse 含 1/N，等价 np.fft.rfft/irfft）。`DpdfNetProcessor`/流式 STFT 保留给 Mic Demo。
- 数值验证（纯 Python 复刻同一 STFT/ISTFT，identity）：步骤1-5 重建 reflect-padded 信号误差 ~1e-13，帧数/长度自洽（waveE==xpad）。identity 整链不含模型内部 ~4hop 延迟故不直接对齐 x，但 postprocess_spec 的 `win_len*2` 裁剪正是抵消真实模型 CyclicBuffer ~4hop 延迟，故真实模型下与源码逐帧一致。
- 注意：初始 state 用公式重建（零依赖）与源码 metadata 精确值有 ~7.6e-6 差；模型为 onnxsim 剥离 metadata 版，源码 infer 跑的是带 metadata 模型。此为零依赖固有微差，非本次主因。README 已更新（离线/实时两路径区分）。
